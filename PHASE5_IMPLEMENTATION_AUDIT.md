## 2. Subsystem-by-Subsystem Audit

### Subsystem 1: OSM Data Service
- **Source File:** `backend/app/services/osm_service.py` (`OSMDataService`)
- **Existing Functionality:**
  - Queries Overpass API or direct OSM 0.6 tile endpoints with local caching in `backend/data/osm_cache/`.
  - Parses raw OSM XML/JSON nodes and ways into GeoJSON `FeatureCollections` with highway classification and building tags.
- **Current API Endpoints:**
  - `POST /api/osm/refresh` (refreshes cache from live mirrors).
- **Actual Input Data:**
  - Cached files: `chennai_buildings.geojson`, `chennai_roads.geojson`, `assam_buildings.geojson`, `assam_roads.geojson`, `wayanad_buildings.geojson`.
- **Missing Functionality:**
  - Lacks spatial indexing (R-Tree / Shapely `STRtree`) for rapid querying of large building datasets (27,884 features).
  - No explicit validation of geometry validity (`is_valid`, self-intersections, slivers) before downstream spatial joins.
- **Required Modifications:**
  - Add geometry validation and bounding-box spatial index filtering.

### Subsystem 2: Building Damage / Exposure Analyzer
- **Source File:** `backend/app/services/damage_analyzer.py` (`analyze_flood_damage`)
- **Existing Functionality:**
  - Extracts vector contours from binary flood masks using OpenCV `cv2.findContours`.
  - Samples up to 250 building centroids and inspects a $3 \\times 3$ pixel neighborhood around the centroid.
  - Computes simple summary counts and mock population metrics.
- **Current API Endpoints:**
  - Called internally inside `_execute_full_geospatial_pipeline` via `POST /api/analyze`.
- **Actual Input Data:**
  - `seg_mask` (uint8 2D numpy array), `bbox` ($[\\text{min\_lat}, \\text{min\_lon}, \\text{max\_lat}, \\text{max\_lon}]$), `preset_id`.
- **Missing Functionality & Defects Identified:**
  1. **Centroid-Only Sampling:** Uses a single center point + $3 \\times 3$ pixel window rather than computing actual polygon footprint overlap against the raster.
  2. **Non-Standard Categories:** Employs `CRITICAL_SUBMERGED`, `MODERATE_BUFFER_RISK`, `SAFE_DRY` rather than project-defined exposure percentages.
  3. **Synthetic Water Depth Fabrication:** Generates synthetic water depths (`2.5 + (idx % 7) * 0.8`), which directly violates Phase 5 instructions ("Do not invent depth values from a binary flood mask").
- **Required Modifications:**
  - Implement genuine polygon rasterization / spatial overlap calculation using `rasterio.features.rasterize` or Shapely polygon-pixel intersection.
  - Implement standard exposure categories:
    - `HIGH_EXPOSURE`: $\\ge 50\%$ footprint overlap.
    - `MODERATE_EXPOSURE`: Between $10\%$ and $50\%$ overlap.
    - `LOW_OR_NO_DETECTED_EXPOSURE`: $< 10\%$ overlap.
    - `UNKNOWN`: Insufficient valid pixels or outside raster bounds.
  - Remove fabricated water depth calculations; report depth as `null` or omit when only binary flood masks are provided.
  - Output standard GeoJSON FeatureCollection with exact exposed area percentages, valid sampled pixel counts, and OSM identifiers.

### Subsystem 3: Rescue Routing & Road Hazard Service
- **Source File:** `backend/app/services/rescue_router.py` (`compute_osm_rescue_routes`)
- **Existing Functionality:**
  - Iterates over OSM road LineStrings, samples flood values along line segments.
  - If any Class 2 flood pixel is touched, flags the road as blocked.
  - Builds NetworkX graph `G_safe` (unblocked edges) and `G_all` (all edges).
  - Computes A* routes between an automatic high-ground command base and 3 hard-coded destination anchors.
- **Current API Endpoints:**
  - Called inside `POST /api/analyze`.
  - `POST /api/route-dynamic` (recalculates route with custom base and depth).
- **Actual Input Data:**
  - `seg_mask`, `bbox`, `preset_id`.
- **Missing Functionality & Defects Identified:**
  1. **Binary Road Blocking Only:** Classifies roads strictly as passable or blocked with zero degrees of hazard. Lacks the required multi-tier hazard classification:
     - `POTENTIAL_HAZARD`: $\\ge 30\%$ valid samples intersect flood mask.
     - `CAUTION`: Between $5\%$ and $30\%$.
     - `NO_DETECTED_INTERSECTION`: $< 5\%$.
     - `UNKNOWN`: Outside raster coverage or insufficient samples.
  2. **Rigid Destinations:** Only routes to 3 preset coordinates; cannot route between arbitrary user-selected start and destination coordinates.
  3. **No Configurable Hazard Penalty:** Graph completely removes edges rather than supporting cost functions with configurable hazard penalties (`edge_cost = road_length_m * hazard_multiplier`).
- **Required Modifications:**
  - Implement road hazard sampling with exact sample counts and percentage calculations.
  - Add configurable cost function supporting both hazard exclusion and hazard penalty multiplier ($1.0\\times$ for safe, $3.0\\times$ for caution, $10.0\\times$ or exclusion for potential hazard).
  - Support arbitrary start and destination coordinates with snapping to nearest road graph nodes.
  - Return comprehensive route summaries, edge breakdowns, and GeoJSON features.

## 4. Phase 5.1 Integrity Audit & Forensic Reconciliation Pass

Following the initial Phase 5 delivery, an academic integrity audit was conducted to resolve reporting discrepancies, enhance graph modeling, and verify data provenance:

### 4.1 Transit ETA Forensic Reconciliation
- **Discrepancy:** The initial report cited 9.4 minutes for a 3,469.2 m route at 25 km/h, whereas theoretical calculation gives:
  $$\text{ETA}_{\text{minutes}} = \frac{3469.2 / 1000}{25.0} \times 60 = 8.32608 \approx 8.33\text{ minutes}$$
- **Root Cause:** The underlying script used an assumed speed of 28.0 km/h and added an undocumented hardcoded 2-minute tactical dispatch buffer: `(3.469 / 28.0) * 60 + 2.0 = 9.4`.
- **Resolution:** Removed the arbitrary buffer, bound `speed_kmh=25.0` in `config.py` and `rescue_router.py`, and synchronized frontend and backend outputs to **8.33 minutes**.

### 4.2 OSM One-Way Directed Connectivity (`nx.DiGraph`)
- **Limitation:** The initial graph was an undirected `nx.Graph`, failing to enforce one-way restrictions on urban arterial corridors.
- **Enhancement:** Converted `build_road_graph` to `nx.DiGraph`:
  - `oneway=yes`: Forward edge $(u, v)$ only; reverse prohibited.
  - `oneway=-1`: Contraflow reverse edge $(v, u)$ only; forward prohibited.
  - `oneway=no`: Bidirectional edges $(u, v)$ and $(v, u)$.
  - Missing tag default: `motorway`, `motorway_link`, and `roundabout` default to forward-only; other road classes default to bidirectional.
- **Verification:** Unit tests 16–18 verify that prohibited reverse travel along one-way streets is rejected (`NO_SAFE_ROUTE_AVAILABLE`).

### 4.3 Terminology Correction
- **Discontinued Labels:** `PASSABLE_VERIFIED_OSM`, `100% hazard-free corridor`.
- **Approved Honest Label:** `CANDIDATE_ROUTE_AVOIDING_MAPPED_HAZARDS`.
- **Disclosure:** The path is a mathematical candidate route based on available OSM geometries and the satellite flood-risk raster, not physical ground-truth road condition verification.

### 4.4 Sample Selection Transparency
- **Buildings:** Systematic uniform stride decimation across serialized Overpass GeoJSON file sequence (`step = 27884 // 1000 = 27`, yielding 1,000 structures in 0.56s). This is a deterministic decimation, not a random or spatially stratified sample.
- **Roads:** First 1,000 LineStrings in file sequence for hazard distribution statistics; full 5,272-road network (673.4 km) for real-time A* routing.

### 4.5 Satellite Flood Raster Provenance (`provenance_024d3597.json`)
- Derived model prediction from `DualStreamAttentionUNet_v2.1` with Hann cosine sliding-window inference over CDSE-ingested genuine Sentinel-2 MSI (`CDSE_SENTINEL-2_20250101_13.01_80.22`, 2025-01-01) and Sentinel-1 C-SAR IW GRD (`CDSE_SENTINEL-1_20251110_13.01_80.22`, 2025-11-10) observations. Classes: 0 (Dry, 49.1%), 1 (Permanent Water, 28.9%), 2 (Flood, 21.9%), 255 (NoData).

## 5. Phase 5.2 Final Technical Verification & MultiDiGraph Audit

A final technical verification was performed to audit directed graph construction, strict hazard avoidance, exact raster pixel counts, and satellite provenance:

### 5.1 MultiDiGraph Migration & Parallel Edge Preservation
- **Finding:** 993 directed node pairs in Chennai feature parallel road segments (e.g., dual carriageways, service roads alongside arterial corridors).
- **Migration:** `build_road_graph` was migrated from `nx.DiGraph` to `nx.MultiDiGraph`.
- **Outcome:** Preserved all 993 parallel road segments with their distinct `osm_id`, highway types, and hazard statistics. `calculate_astar_evacuation_route` selects the minimum-weight parallel edge during path reconstruction.
- **Scale:** 15,055 nodes and 33,056 directed edges built in 0.27s.

### 5.2 Strict Hazard Avoidance Audit
- When `avoid_hazards=True`, `POTENTIAL_HAZARD` edges are strictly excluded from the graph.
- Verified in `test_21`: when all available paths cross a flood hazard, `calculate_astar_evacuation_route` returns `NO_SAFE_ROUTE_AVAILABLE`. When `avoid_hazards=False`, the path is found with the 10x penalty.
